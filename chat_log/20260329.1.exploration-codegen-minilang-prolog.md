# Session: exploration-codegen-minilang-prolog (EXPLORATION NOTES, not a resume point)

## What this is
Research spirals from the fixedpoint-codegen session. Ideas explored, validated mechanically, but parked because compression ratio didn't justify complexity for a single use case. Useful reference if the project grows to need them.

## Exploration 1: Cursor scalar mini-lang

The idea: a model whose property types are distinct scalars that the codegen fn dispatches on. The Ns model is the API surface, dot access is type-checked, the fn reads scalar names to know what computed value to fill in.

```tsp
scalar NsPath extends string;
scalar NsName extends string;
scalar NsMethod extends string;

model Ns {
  path: NsPath;
  name: NsName;
  method: NsMethod;
}

model RoutesPattern {
  `Ns.path`: {
    path: Ns.path;      // fn sees Scalar(NsPath), fills with computed path
    method: Ns.method;  // fn sees Scalar(NsMethod), fills with computed method
    name: Ns.name;      // fn sees Scalar(NsName), fills with computed segment
  };
}
```

**Validated:** fn can read prop.type.type and see distinct Scalar names. Backtick keys work. Compiler checks Ns.path resolves correctly, Ns.banana errors.

**Limitation:** Ns.path works as property TYPE but fails as template ARGUMENT. ModelProperty resolves differently in template arg position vs type position.

**Why parked:** For one use case (routes), hardcoding the walk logic in 60 lines of JS is simpler than maintaining the scalar vocabulary + Ns model + pattern model. The mini-lang pays off at 3+ different namespace projections.

## Exploration 2: Opcode vocabulary models

The idea: marker models as instructions the fn interprets.

```tsp
model Literal {}    // copy namespace export as string literal
model Collect {}    // gather child exports into flat model
model Recurse {}    // apply spec recursively to children
model Ref {}        // emit reference to original namespace node
```

Spec models compose from these opcodes:

```tsp
model RouteEntry {
  template: Literal;
  method: Literal;
  params: Collect;
}

model RouteTree {
  entry: RouteEntry;
  children: Recurse;
}
```

**Why parked:** Adding a new opcode requires updating both the vocabulary AND the fn interpreter. The abstraction layer between "what you want" and "what happens" adds indirection without reducing total code. Direct JS is more legible for a single use case.

## Exploration 3: Spec model as the walker (approach 3 from the session)

Each property type IS an instruction. The fn reads property types and dispatches:

- String literal with {var} → interpolate
- Model reference → recurse into child namespace
- Marker model → special behavior (collect, flatten, etc.)

The model body is a program in a 4-word language. The fn is the interpreter.

**Why parked:** Same indirection problem as opcode vocabulary. The "language" has 4 words. Writing a new fn is faster than learning a new DSL.

## Exploration 4: No spec model, namespace-only (approach 4)

The namespace IS the output structure. Decorators mark gaps. TSP namespace merging lets the autozone reopen namespaces and inject computed aliases.

```tsp
namespace todos {
  namespace create {}
  @param("string") namespace id { ... }
}

// autozone merges in:
namespace todos {
  model route { template: "/todos"; method: "GET"; }
  namespace create {
    model route { template: "/todos/create"; method: "POST"; }
  }
}
```

**Validated:** namespace merging works. The fn can reopen any namespace and add declarations.

**Why parked:** The output looked cluttered. User preferred clean separation between "what I wrote" and "what was derived."

## Exploration 5: Prolog engine embedding

Tau Prolog (pure JS) inside the codegen fn. Namespace tree auto-extracted as Prolog facts. Rules in a .pl file next to the .tsp file. Query results materialized as TSP source.

```js
const session = pl.create();
session.consult(nsToFacts(ns) + userRules);
session.query("route(Path, Method, Params).");
// collect answers, write autozone
```

```prolog
route(Path, Method, Params) :-
    namespace(N, _),
    crud(N, Method),
    compute_path(N, Path),
    findall(P-T, param_in_path(N, P, T), Params).
```

**Why parked:** The binding goes the wrong direction. Facts get extracted to JS-land and queried there, rather than TSP declarations serving as the fact base directly. Also, the user wants to learn Prolog deeply through hands-on practice, not have AI embed it as a black box.

## Exploration 6: Single-model transform with template args

The dream syntax:

```tsp
model RoutesPattern {
  `$ns.path`: RouteParam<$ns.path, $ns.autoParams>;
}
```

One model = the whole transform. Dynamic key from cursor, value is a template instantiation with cursor refs as args.

**Why it fails:** TSP model property access (Ns.path) resolves to ModelProperty in template argument position, which is not assignable to the template constraint (string). Works as property type, fails as template arg. Fundamental: the compiler resolves Ns.path differently depending on where it appears.

## Cross-cutting insight

All explorations converged on the same structural problem: TSP's type system operates at bind time (symbol tables), but the transforms the user wants require check-time or runtime information. The fixed-point loop bridges this by running transforms at check time and writing results back as static source that the binder can process on the next pass. Every mini-lang attempt was trying to avoid that bridge, but the phase separation in the compiler makes it unavoidable.

## The Prolog connection

The user identified that Prolog's unification solves the mapping problem in zero code:
- TSP namespace tree = Prolog facts
- Route conventions = Prolog rules
- Generated models = query results

The compression ratio is orders of magnitude better. The barrier is embedding a Prolog runtime in a TypeSpec codegen fn, which inverts the desired binding direction. The user is studying Prolog separately (hafley-prolog project) and wants to build intuition before deciding where it fits.
