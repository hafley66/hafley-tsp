# Session: decorator-def-wire-extract

## Goal
Wire asyncapi to use generated decorators from a spec definition instead of hand-written ones, extract shared decorator tooling into its own workspace package.

## Current State
- decorator-factory.ts and decorator-codegen.ts extracted from asyncapi into @hafley/typespec-decorator-def (commit 8042246)
- asyncapi depends on decorator-def via workspace:* with sub-path imports (/factory, /codegen)
- asyncapi decorators.ts and lib/decorators.tsp are generated from src/decorator-spec.ts via `pnpm generate`
- @decoratorDef targets param uses Target[] enum instead of string
- 29 tests passing across both packages (18 decorator-def, 11 asyncapi)
- decorator-codegen.ts has factoryImport field so generated output imports from configurable path
- AMQP binding models extracted to lib/models.tsp + src/0_types.ts (domain types separate from decorator infra)

## Problem/Context
The decorator-codegen (JS object spec) is a detour from the original vision of TypeSpec compiles TypeSpec via @decoratorDef. The JS spec works and is wired, but the user wants .tsp models as the source of truth -- not a JS object in decorator-spec.ts. The two-phase compilation approach (compile @decoratorDef models first, emit decorator library, then compile actual program) is the intended end state.

## Solution/Approach
- Two-phase compilation: phase 1 compiles .tsp with @decoratorDef models, emits extern dec declarations + factory .ts; phase 2 compiles the actual program using those generated decorators
- Static LSP checking for decorator args (requires generated extern dec declarations)
- decorator-def package provides: factory primitives, codegen, @decoratorDef TypeSpec decorator, reader, Alloy generator
- asyncapi consumes via workspace dependency

## Key Insights
- decorator-codegen had a bug: options fields spread as positional builder params, but TypeSpec compiler passes options as single bag. Fixed with destructuring.
- factoryImport field on LibrarySpec lets generated decorators.ts import factory from any path (workspace package, relative, etc.)
- Sub-path exports (./factory, ./codegen) keep the package surface clean -- consumers pick what they need without pulling Alloy
- The user explicitly does not want the JS object spec to be the end state. .tsp models with @decoratorDef is the goal.
- The user wants the factory objects exported directly, not individual getter/has functions spread across the export surface.

## Open Questions
- How does two-phase compilation work in practice? Separate tspconfig? A build script that runs tsp compile twice?
- How to handle AMQP binding models (nested structures) in @decoratorDef -- they don't fit the flat param/options model
- Should the Alloy generator (generate.tsx) and string codegen (decorator-codegen.ts) be unified?
- Curried decorators -- TypeSpec functions can't return namespaces, workarounds exist but clunky
