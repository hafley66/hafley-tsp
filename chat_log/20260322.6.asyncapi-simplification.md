# Session: asyncapi-simplification

## Goal
Simplify @hafley/typespec-asyncapi for a first pass, informed by learning AsyncAPI 3.x from the spec and identifying what's actually needed for a collab drawing app proof-of-concept.

## Current State
Design session complete. Identified minimal decorator set and a key unresolved insight about channel/route unification. Ready for implementation but letting the abstraction compost first.

## Problem/Context
The initial AsyncAPI library (commit 62ba5d2) mapped AsyncAPI's full object model. After learning AsyncAPI ground-up and pressure-testing against the actual target (collab drawing app with architecture roulette), most of that surface area is unnecessary for a first pass and some of the abstractions may be wrong.

## Key Insights

### AsyncAPI in one sentence
AMQP is an RxJS pipeline where every operator (filter, buffer, subscribe) is ripped out of the process, given a name, put on a different machine, made durable, and configured with YAML instead of code.

### AMQP decomposition mapped to RxJS
- Exchange = Subject (publish point)
- Exchange types = filter variants (direct=exact match, topic=glob, fanout=no filter, headers=metadata match)
- Binding = filter() in the pipe (but runtime-mutable, hot-swappable without redeploying)
- Queue = shareReplay that writes to disk and survives process restarts
- Consumer = subscribe() with explicit ack (backpressure with rollback)
- Prefetch = mergeMap concurrency parameter

### AMQP's legitimate gaps (not over-engineering, actually missing)
1. No ordered-by-key parallelism (Kafka's partitions solve this)
2. Closed routing predicate set (4 fixed exchange types, can't define custom)
3. No first-class retry/backoff (everyone builds TTL queue Rube Goldberg machines)
4. No schema evolution story (message bodies are opaque bytes)
5. Exchange-to-exchange composition requires RabbitMQ extensions, not in spec

### The four AMQP primitives are irreducible
Exchange, binding, queue, consumer are genuinely orthogonal. Remove any one and you lose a capability. But only queue and message deserve URLs (store data / cross borders). Exchange and binding are routing configuration, not resources.

### Channel = Route, period
A route is a channel where transport=HTTP and message count=1 per direction. A channel is a route where message count=0..N and the transport might buffer. @channel and @route are the same decorator with different transport assumptions.

### The migration story is the killer feature
Describe existing coupled code in TypeSpec. Add transport decorators at the seam. Generate bridge code (client stubs + server handlers). Swap one side to use generated client. Manual business logic never changes. Move the cut point by changing decorators and regenerating. "Zip over the wound."

### Recursive channel structure
Every field of a channel is itself a channel. A room is a channel. A stroke stream within a room is a channel. A single stroke event is a channel of depth 1. The fundamental unit is: a named scope owns some inputs and some outputs, and transports are serialization strategies for crossing the scope boundary.

### send/receive is ownership declaration
Not behavior. It declares which side of the pipe this application is on. "I produce into this pipe" vs "I consume from this pipe."

## First Pass: Minimal Decorator Set

### Keep (3 decorators)
- `@channel(address)` -- names the pipe
- `@send` / `@receive` -- declares pipe ownership side
- `@payload` -- marks message body (parallel to @body for HTTP)

### Defer (useful but not first pass)
- `@server` -- hardcode or infer from channel protocol
- `@reply` -- drawing app's request-reply paths are HTTP (already works)
- `@correlationId` -- only needed for reply matching
- `@messageHeader` -- convention: non-payload params are headers
- `@contentType` -- default to application/json

### Cut from first pass (YAGNI)
- `@amqpBinding` -- protocol-specific infra config is the emitter's problem
- `@amqpOperationBinding` -- operational knobs, not design-time declarations

## Proof-of-Concept Target: Collab Drawing App

### Why this target
- Small data model (Stroke, Point, Room, User, Canvas -- ~5 types)
- Exercises all transport patterns (bidi stream, request-response, server stream)
- Architecture roulette: same TypeSpec source, generate for WS-only, HTTP+WS, AMQP+HTTP
- Small enough to hand-verify every generated output

### Transport patterns needed
- Stroke events: bidi stream (WS or AMQP fan-out)
- Canvas load/save: request-response (HTTP)
- Auth: request-response (HTTP)
- Presence: server stream (WS or SSE)
- Undo/redo: ordered command stream with causal ordering

### Sketch TypeSpec source
```typespec
import "@typespec/http";
import "@hafley/asyncapi";

using Http;
using AsyncAPI;

model Point { x: float32; y: float32; }
model Stroke { points: Point[]; color: string; width: float32; }
model Room { id: string; name: string; }

@route("/rooms")
namespace Rooms {
  op create(@body room: Room): Room;
  op get(@path id: string): Room;
}

@channel("/rooms/{roomId}/strokes")
namespace StrokeStream {
  @send op draw(@payload stroke: Stroke): void;
  @receive op onStroke(@payload stroke: Stroke): void;
}

@channel("/rooms/{roomId}/presence")
namespace Presence {
  @send op join(@payload user: string): void;
  @send op leave(@payload user: string): void;
  @receive op onPresence(@payload user: string): void;
}
```

## Open Questions (evolved from previous session)
- Channel as recursive scope: if every field is a sub-channel, should the TypeSpec model reflect nesting explicitly or keep it flat with address patterns?
- send/receive may be unnecessary for WS (both sides do both). Only meaningful when the transport is asymmetric (AMQP publisher vs consumer). For WS, direction is per-message, not per-operation.
- Should @channel just be @route with a different transport inference? Or keep them separate for clarity?
- Sessions/rooms as models vs interfaces vs async lifecycles -- how to express "this scope has a lifecycle (connect/disconnect)" vs "this scope is always available"

## Deeper Insight: Channels Are Stateful Processes, Not Pipes

AsyncAPI models channels as typed pipes (address + message schemas). But the actual primitive is an async generator / scan-reducer with a lifetime:

```
Channel<Address, State, Inputs, Outputs, Reducer>
```

- **Address** = channel identity (params like roomId)
- **State** = the scan accumulator (canvas state, participant list)
- **Inputs** = discriminated union of events the channel accepts (draw, undo, join)
- **Outputs** = discriminated union of events the channel emits (delta, snapshot, presence)
- **Reducer** = (State, Input) -> State

Outputs are projections/selectors over State. An RTK slice is close to the right shape. An async generator is the honest runtime primitive: params are the address, yield is output, next() is input, the loop body is the reducer, generator lifetime is the channel lifetime.

The hard part: inputs and outputs are entangled through the reducer. The set of valid inputs depends on current state. The output type depends on which input triggered it. yield and next() types are not independent.

AsyncAPI doesn't model this. It says "this channel carries these message types" -- a wire format description. The gap between that and "this channel is a stateful reduction over an event stream with typed projections" is the gap between describing serialization and describing computation.

Transport is orthogonal: where does the reducer run, and how do inputs/outputs cross the process boundary? Same reducer, different serialization strategy at the boundary.

## Axis Correction: Server/Client, Not Send/Receive

send/receive is the wrong decomposition. Both sides send AND receive. The correct axis is **server/client** because it declares where state lives:

- **Server side**: accepts input events, owns the reducer, emits state projections
- **Client side**: emits input events, receives state projections, owns no state

The RxJS shape for the server side:
```typescript
mergeByKey({ strokes: stroke$, presence: presence$, undo: undo$ })
  .pipe(scan((state, event) => { switch(event.key) { ... } }, init))
```

TypeSpec's role is NOT to express the pipe. It declares:
1. The input event union (merge keys + types)
2. The state type (scan accumulator)
3. The output projections (what clients see)
4. The boundary location (where the scan runs)

The reducer body and projection transforms are manual code inside the generated scaffold. TypeSpec declares the typed holes at process boundaries. The piping language stays in the target language (Rust/TS).

This means @send/@receive should probably become @server/@client or something that declares state ownership, not message direction.
