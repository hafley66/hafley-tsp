# Session: binding-core-package-design

## Goal
Design and build a reusable TSP binding core package (@hafley/typespec-binding-core) that provides namespaced decorators (Entity, Rel, Bind) for mapping external data sources (CLI output, HTTP APIs) into local storage (SQLite). Prove the pattern is source-agnostic by declaring ghcacher entities.

## Current State
- Package created at packages/binding-core/ with three namespaced decorator libraries
- Entity { pk, unique, manual, index } -- storage model decorators
- Rel { belongsTo, hasMany, hasOne, manyToMany } -- relation decorators (refactored from routes-graph-test)
- Bind { from } -- source-to-target mapping decorator
- ghcacher example at examples/ghcacher/ with 3 entities (repo, pull_request, notification) compiling clean
- Source models (GhPullRequest, GhRepo, GhNotification) in camelCase, target models in snake_case
- Binding models declare renames/transforms, auto-mapping by name match, dot-path backtick fields for nested flattening
- Uses decorator-factory.js (flagDec, listDec, objectDec) from @hafley/typespec-decorator-def
- Rel decorators use custom logic: Symbol.for("hafley:relations"), string-keyed stateMap, AST parent walk

## Key Technical Details

### Three-artifact pattern (per entity)
1. Source model -- wire format, native naming (camelCase for GH, whatever for Jira/Stripe)
2. Target model -- storage format, snake_case, flat, Entity/Rel decorators
3. Binding model -- only the exceptions (renames, transforms). Same-name fields auto-map. Dot-path fields auto-resolve.

### Decorator soup strategy
Decorators go directly on entity models. Alternate input surfaces (parallel config models, binding models per concern) available for UI/grid/etc. concerns if soup gets too thick. For now, decorator soup is fine because namespacing keeps it organized.

### Dot-path backtick convention
`author.login` as a backtick field name means "flatten source.author.login into this column". All dot-path fields must be nullable (enforced at compile time). The field name itself encodes the extraction path.

### Binding chain validation
@Bind.from stores source + target model refs. Property chains are tuples of ModelProperty refs: [GhPullRequest.headRefName] for renames, [GhPullRequest.owner, GhUser.login] for nested access. Validated at compile time by walking the chain -- each element's type must host the next element.

### Factory pattern gaps
decorator-codegen generates .tsp + .ts from a spec for standard patterns (flag, value, object, list, exclusive). Doesn't cover: Rel.* (custom AST walk + string-keyed stateMap), Bind.from (Model refs + chain validation), multi-namespace $decorators map. Entity.pk and Entity.manual are fully generatable. Entity.unique and Entity.index need ModelProperty[] param support added to codegen.

### Phase ordering (inherited from routes-graph-test)
Rel decorators fire during model type checking. $onValidate runs post-check. Binding chain validation must happen in $onValidate. stateMap keyed by model name STRING not type object (phase stability across modules).

## Architecture (from earlier this session)

```
DECLARATION                    FACT DB (EDB)              RULES (IDB)            EMITTERS
folders/ entity.tsp     -->    field, relation,    -->    left joins     -->     SQL, Rust, TS,
@decorators                    binding_map,               between fact           GraphQL, Prolog
source models                  source, pk,                tables
binding models                 unique_key, manual
```

Each extractor appends rows to fact tables. Rules are joins. Emitters write query results to disk in autozone blocks. Left join = opt-out (empty table = rule produces nothing).

## Gaps identified (not yet built)

1. $onValidate fact extractor -- decorators store state, nothing reads it yet
2. SQL emitter -- no emit-sqlite.js exists
3. Rust emitter bridge -- @hafley/alloy-rs exists but nothing connects fact tables to Alloy components
4. Binding chain validation -- @Bind.from stores models but doesn't validate property chains
5. decorator-codegen improvements -- multi-namespace support, ModelProperty[] params
6. Remaining ghcacher entities (9 of 14 tables missing)
7. Jira demo (same libraries, different source models)
8. Junction table pattern (@Entity.junction for composite PK, no autoincrement)
9. Union strategy plugin (@Union.strategy for sum types in SQL)

## Broader vision (from conversation)

- @crud as higher-order decorator (macro over full pipeline, only valid when end-to-end path exists)
- @streamable for connection-as-entity + event->invalidation map (RTK Query tags from API level)
- sprefa comment annotations for extracting facts from existing Rust/TS/SQL code
- Prolog as rules engine for constraint satisfaction (valid moves, not generation)
- Incremental adoption tiers: Tier 0 (hand-written) -> Tier 1 (decorators) -> Tier 2 (@crud) -> Tier 3 (reconciliation)
- System is fundamentally a Datalog database: extractors = EDB, rules = IDB, emitters = queries writing results to disk
