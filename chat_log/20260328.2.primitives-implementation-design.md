# Session: primitives-implementation-design

## Goal
Design concrete implementation of the 39-primitive taxonomy using existing toolset (decorator-def factory, decorator-codegen, emit-helper TargetLang, Alloy JSX). Map from TSP decorators through resolution/validation to target-specific emission.

## Current State
Full implementation architecture designed across 5 layers. No code written. Ready to start with enumDec factory primitive and a minimal primitives package.

## Problem/Context
Have 39 primitives across 6 namespaces (temporal, spatial, rx, intent, delivery, lifecycle) plus 10 named pattern combos. Need to wire these through the existing decorator-def → emit-helper → Alloy pipeline so that decorators on TSP models produce target-specific code.

## Solution/Approach

### 5-Layer Pipeline

```
TSP source (decorators applied)
  → Program.stateMap (raw decorator state)
  → resolveIntent() folds all keys into ResolvedIntent object
  → validateIntent() checks combo coherence
  → emitWithIntent() dispatches on temporal shape to IntentEmitter
  → Alloy JSX render with AutoZone/ManualZone
```

### Layer 1: Primitives as Decorators

New factory primitive needed: `enumDec` for N-way exclusive sets.
- `enumDec<T>(key, values[])` returns per-value decorator + shared accessor
- Each value is a flat decorator (no string args): `@call`, `@stream`, `@bidi`
- All write to same state key, validation ensures only one set per target
- Flags use existing `flagDec` for booleans: `@hot`, `@fallible`, `@idempotent`

Decorator-spec per namespace:
- temporal: enumDec(6) → call, fire, stream, sink, drain, bidi
- spatial: enumDec(4) → unicast, broadcast, merge, mesh
- intent direction: enumDec(3) → read, write, readwrite
- delivery guarantee: enumDec(3) → at_most_once, at_least_once, exactly_once
- overflow: enumDec(4) → buffer, drop_old, drop_new, concurrent
- combine: enumDec(5) → merge, latest, zip, race, join
- cancel: enumDec(3) → cooperative, forced, none
- flags(11): async, hot, replay_last, replay_all, optional, fallible, idempotent, once, reusable, ordered, unordered

decorator-codegen generates flat TSP externs:
```typespec
extern dec call(target: Model | Union);
extern dec fire(target: Model | Union);
extern dec stream(target: Model | Union);
// etc -- no string args
```

### Layer 2: ResolvedIntent (the fold)

```typescript
interface ResolvedIntent {
  temporal: "call" | "fire" | "stream" | "sink" | "drain" | "bidi";
  spatial: "unicast" | "broadcast" | "merge" | "mesh";
  rx: {
    async: boolean;
    hot: boolean;
    replay: "last" | "all" | null;
    overflow: "buffer" | "drop_old" | "drop_new" | "concurrent" | null;
    combine: "merge" | "latest" | "zip" | "race" | "join" | null;
  };
  intent: {
    direction: "read" | "write" | "readwrite";
    optional: boolean;
    fallible: boolean;
    idempotent: boolean;
  };
  delivery: {
    guarantee: "at_most_once" | "at_least_once" | "exactly_once" | null;
    ordered: boolean;
  };
  lifecycle: {
    consumption: "once" | "reusable";
    cancel: "cooperative" | "forced" | "none";
  };
}
```

resolveIntent(program, target) reads all state keys, folds into this object with defaults:
- temporal defaults to "call"
- spatial defaults to "unicast"
- rx defaults to all false/null
- intent.direction defaults to "read"
- lifecycle defaults to "reusable" + cancel "none"

### Layer 3: Validation (constraint checking)

Enumerable rules:
- overflow requires stream/sink/bidi temporal
- combine requires spatial.merge
- hot requires async
- replay requires hot
- fire + fallible is contradictory (no response channel)
- delivery guarantees require async
- drain + fallible contradictory
- once + reusable contradictory (mutual exclusion)
- ordered + unordered contradictory

### Layer 4: IntentEmitter interface

```typescript
interface IntentEmitter<TDecl> {
  emitCall(model: ModelDef, intent: ResolvedIntent): TDecl;
  emitStream(model: ModelDef, intent: ResolvedIntent): TDecl;
  emitSink(model: ModelDef, intent: ResolvedIntent): TDecl;
  emitBidi(model: ModelDef, intent: ResolvedIntent): TDecl;
  emitFire(model: ModelDef, intent: ResolvedIntent): TDecl;
  emitDrain(model: ModelDef, intent: ResolvedIntent): TDecl;
  emitReducer(state: ModelDef, events: UnionDef, intent: ResolvedIntent): TDecl;
  emitCombine(sources: ModelDef[], strategy: ResolvedIntent): TDecl;
}
```

Walker dispatches on intent.temporal to the right method. Each target implements all 8 methods. The ResolvedIntent object carries all the context needed for the target to make decisions (hot? fallible? overflow policy?).

### Layer 5: Alloy Integration

Alloy JSX target implements IntentEmitter with refkeys and zones. Example for stream:
- AutoZone: function signature derived from model + intent
- ManualZone: function body for user implementation
- Conditional generation: hot + replay_last → watch channel setup, fallible → Result wrapping

### Pattern Aliases

Named combos expand to primitive sets at resolution time:
```
pattern.http_endpoint = temporal.call + rx.async + intent.fallible + lifecycle.reusable
pattern.subscription  = temporal.stream + rx.async + rx.hot + intent.read + lifecycle.cancel.cooperative
// etc (10 patterns defined)
```

Can be implemented as TSP template models that apply all constituent decorators.

## Key Insights
- enumDec (N-way exclusive) is the missing factory primitive -- most namespaces are exclusive sets
- ResolvedIntent is a single flat object, not a tree -- fold all decorator state into one place for easy dispatch
- Validation rules are finite and enumerable -- hot implies async, overflow implies stream, etc.
- IntentEmitter has 8 methods (6 temporal + reducer + combine) -- bounded interface per target
- Alloy integration: AutoZone for signatures derived from intent, ManualZone for user implementation bodies
- Pattern aliases are just template models that apply multiple decorators -- no special compiler support needed
- The pipeline is: stateMap → fold → validate → dispatch → render. Each step is a pure function except render.

## Open Questions

- Where does @state(EventUnion) fit in the primitives package vs a separate event-sourcing package?
