# Session: reactive-pipe-semantics-for-tsp

## Goal
Exploring what semantic primitives sit at the intersection of all target languages, and whether TSP can express them. Evolved from the universal expression components rejection into a deeper question about liftable semantics.

## Key Thread

### Universal expression components: rejected
Full design (889 lines) for JSX Let/If/For/Call/Await/Try components was explored and rejected as not worth the ceremony. The semantic mismatch between languages (Rust ? vs Go if err != nil vs TS try/catch) makes universal expression emission more work than string concat. Design doc preserved at chat_log/20260331.3.universal-expression-components-design.md.

### The actual semantic intersection
Not let/if/for (imperative). The liftable intersection is container + combinator + effect:
- Containers: Option, Result, Array, Iterator, Future, Stream/Observable
- Combinators: map, flatMap, filter, reduce, zip, chain, collect
- Effects: fallible, concurrent, stateful, IO

Every container in every language supports the same combinators. RxJS proved this for async. Rust iterators proved it for sync. Haskell proved it for everything via typeclasses.

### TSP's wall
TSP has types (nouns) but no arrow types (verbs). No A -> B. No way to say "this stage takes Stream<Response> and produces Stream<Page>" at the type level. Can't type-check that pipe stages compose. The `op` keyword is closest but describes API operations, not composable stages.

### Pipes as class composition
An RxJS pipeline is a linked list of class instances. Each operator constructs a new Observable wrapping the previous. A typed pipe is really a class composition chain where generics flow left to right: MapStage<A,B> -> FilterStage<B> -> ScanStage<B,Acc>.

This is the same thing TSP generics already do (Paginated<WithTimestamps<Repo>>) but inside-out instead of left-to-right.

### The RxJS operator canon (~25 operators)
Transform: map, filter, flatMap/mergeMap, switchMap, concatMap, exhaustMap, reduce, distinct
Combine: merge, combineLatest, zip, concat, forkJoin, withLatestFrom  
Time/State: scan, debounce, throttle, delay, retry, timeout, startWith, pairwise
Materialize: toArray, toPromise, materialize, share, shareReplay, refCount

Each has well-defined type signatures. Each has known lowerings to imperative code per target language.

### User's vision
A reactive pipeline language that:
- References TSP models as its type vocabulary
- Has arrow-typed operators (the RxJS set)
- Is linear (chains with merge/fork points, not arbitrary trees)
- Compiles to the same emitter pipeline that currently reads decorators
- Bridges to consumption patterns (react-query, SQLite upsert, etc.)

### Borrow checking as Prolog
Polonius (Rust's borrow checker) is literally a Datalog program. The constraint space for generated code is fully known at emit time (we generate all access patterns). A Prolog backtracker could theoretically derive &/&mut/owned annotations from access pattern facts. Not worth building since emitter templates already encode the right ownership patterns for the regular structures they generate.

## Problem/Context
TSP is deliberately not a programming language. Decorators are annotations, not operations. The richer the intent to express, the more the emitter compensates for what TSP can't say. The current sync emitter infers implicit pipelines from stacked decorators -- making them explicit requires something TSP's grammar can't express natively.

## Open Questions
- Could a .pipe file or pipe block inside a TSP namespace reference TSP types while adding arrow composition?
- Previous sessions explored a "mode for a namespace" that might enable this -- revisit
- Is this worth building or does the decorator-stacking approach scale far enough?
- How do merge/fork points work in a linear pipe syntax? (merge is N inputs -> 1 output)
