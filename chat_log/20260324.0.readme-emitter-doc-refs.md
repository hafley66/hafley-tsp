# Session: readme-emitter-doc-refs

## Goal
Design emitter capabilities for auto-generating README.md docs, target-language doc comments, deep path enumeration, and typed doc references from TypeSpec definitions.

## Current State
Design phase complete. Full design doc written to `docs/design/readme-emitter-and-doc-refs.md`. No implementation started.

## Problem/Context
The neutral type adapter (`TypeDef[]`) already declares `doc?: string` on all types but never populates it. Three call sites need wiring to unlock four downstream capabilities. The `DocComment` Rust component exists in `@hafley/alloy-rs` but is unused by the emitter.

## Solution/Approach
Four capabilities, all feeding from the same `TypeDef[]` pipeline:

1. **README emitter** -- markdown per directory, co-located with .tsp files. Preserves hand-written content above `<!-- tsp:generated -->` marker.
2. **Target-lang doc comments** -- wire `doc` through existing emitters (Rust `///` via DocComment component, TS `/** */`, etc.)
3. **Deep path enumeration** -- lodash-style paths through model graph (like react-hook-form), filterable by decorator. Emits exhaustive match arms.
4. **Doc references** -- `{ModelName}` tokens in doc strings resolve to language-native links (rustdoc `[`Customer`]`, JSDoc `{@link}`, markdown anchors, Sphinx `:class:`). Deep path refs like `{Customer.address.city}` also supported.

## Key Insights
- Alloy core has no Rust doc comment component; DocComment is ours in `@hafley/alloy-rs`
- The adapter's neutral types already carry `doc?: string` everywhere -- it's a wiring gap, not a design gap
- Filesystem-as-outline means README link topology mirrors namespace topology
- Doc references compose with deep paths: `{Customer.address.city}` resolves as both a type ref and a path

## Open Questions
