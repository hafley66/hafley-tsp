# Session: route-convention-graph-extraction

## Goal
Build file-system routing convention with compile-time route table generation AND entity-relation graph extraction from TSP model decorators. Prove that both the tree (routes) and graph (relations) projections can be extracted from the same source at compile time.

## Current State
- Route convention: VALIDATED AND WORKING (62 routes across 5 entities in examples/routes/)
- Graph extraction: VALIDATED AND WORKING (4 entities, 6 edges, 3 cycles detected in examples/routes-graph-test/)
- Method resolution: FINALIZED (all CRUD verbs collapse, freeform POST/GET)
- Relation decorators: WORKING (@belongsTo, @hasMany, @manyToMany with shared Symbol.for state key)
- Existing fixtures: 17/19 passing (10 and 18 are pre-existing known failures)

## Key Technical Details

### Method Resolution (tools/tsp-validation/lib/route.js)

CRUD_METHODS map: create→POST, read→GET, get→GET, delete→DELETE, update→PUT, updatePatch→PATCH

COLLAPSE_NAMES set: ALL CRUD verbs collapse to parent path. Only freeform names add segments. This gives REST-standard paths: POST /todos = create, GET /todos = read, etc.

STRUCTURAL_NS set: ["query", "mut"] -- walker descends without adding path segment.
SKIP_NS set: ["side", "deps", "flow"] -- walker ignores entirely.

Walk function signature: `walk(namespace, pathPrefix, paramsAccum, insideContainer)` where insideContainer tracks whether we're inside query/ or mut/ to resolve freeform names.

Freeform under mut/ → POST. Freeform under query/ → GET. @POST override for JSON body queries (not yet implemented).

Route table keys use "METHOD /path" format for uniqueness (multiple verbs at same path).

### File System Convention

- Folder name = path segment, snake_case always
- `id_/` postfix underscore = dynamic param folder (Rust-safe, no brackets)
- `entity.tsp` at entity root: model, filter, id scalar, enums
- `routes.tsp` at every path level: query/, mut/ namespace tree
- `side/`, `deps/` only at entity root routes.tsp (not inside id_/ or deeper)
- `flow/` lives outside the route tree entirely
- Import DAG: _types.tsp ← entity.tsp ← routes.tsp ← _scaffold.tsp
- Cross-entity refs in deps/ use fully qualified namespace paths, not file imports

### Relation Decorators

Declared in _types.tsp:
```tsp
extern dec belongsTo(target: unknown);
extern dec hasMany(target: unknown);
extern dec hasOne(target: unknown);
extern dec manyToMany(target: unknown);
```

JS implementation uses shared state key: `Symbol.for("hafley:relations")` -- this MUST be Symbol.for (not Symbol()) so the key is shared between types.js (decorator impl) and graph.js (extraction).

Decorator target is ModelProperty. Parent model name found by walking AST: `target.node` → walk `.parent` until finding node with `.id.sv` and `.properties`.

State stored as: `stateMap(REL_KEY).set(modelName, [{property, kind, targetType}])` keyed by model name STRING, not model type object (because the type object identity isn't stable across phases).

### Graph Extraction

CRITICAL: Graph extraction uses `$onValidate(program)` hook, NOT an extern fn. This is because decorators on model properties fire during model type checking, but extern fn calls fire during alias checking, which happens in unpredictable order. By the time an extern fn runs, the decorator stateMap may be empty. `$onValidate` runs AFTER all types are checked, so all decorator state is available.

The `$onValidate` function receives `program` (not `ctx`). Access stateMap via `program.stateMap(REL_KEY)`.

Graph extractor produces: entity list, typed edges (1:M, M:1, M:M), cycle detection, and route implications per edge type.

### Phase Ordering Discovery

Models declared inside `namespace routes.orgs { model Org { ... } }` do NOT appear in the namespace's `.models` map when accessed from an extern fn at check time. This is a TSP compiler behavior -- the namespace type's models map is populated after the fn has already evaluated. The $onValidate approach sidesteps this entirely by running post-check.

Models at global scope (no namespace wrapper) also don't appear in any namespace's `.models` map via the checker's `getGlobalNamespaceType()`. They exist but aren't findable by namespace traversal during check phase.

### Route ↔ Relation Mapping

Each relation type maps to a distinct route pattern:
- @belongsTo (M:1): query field endpoint, NOT a sub-resource (GET /todos/{id}/owner)
- @hasMany (1:M): sub-resource folder (GET /orgs/{id}/members, GET /users/{id}/todos)
- @manyToMany (M:M): junction folder with link/unlink semantics (POST /todos/{id}/tags/link, not create/delete)

M:1 back-edges and cycles are detected. Back-edges become GET query fields. Cycles are logged as warnings.

### Three Tiers of Automation (designed, not yet built)
- Tier 0: Manual -- write entity.tsp and routes.tsp by hand
- Tier 1: Scaffold -- create folders + entity.tsp, scaffolder generates routes.tsp skeletons with autozone markers
- Tier 2: Full codegen -- @crud decorator, fixed-point loop generates complete CRUD ops

### Auto-discovery Design (designed, not yet built)
- `find api/ -name "routes.tsp"` discovers all route files
- Sort by depth, generate _scaffold.tsp with all imports in autozone
- Adding entity = create folder + routes.tsp + re-run scaffolder
- No root manifest to maintain

## Design Decisions Made This Session

1. ALL CRUD verbs collapse to parent path (REST standard, not /todos/create)
2. Freeform mut names → POST, freeform query names → GET
3. `id_/` postfix underscore for params (Rust-safe)
4. Models in entity.tsp at entity root, routes in routes.tsp at every level
5. side/deps only at entity root (entity-level concerns, not path-level)
6. Relation decorators store by model name STRING not type object (phase stability)
7. Graph extraction via $onValidate not extern fn (phase ordering)
8. Route table keys include HTTP method for uniqueness
9. M:M relations get link/unlink semantics (junction table), not create/delete
10. M:1 back-edges become query fields, not sub-resources

## Unified Architecture (crystallized end of session)

The whole project is one idea expressed in layers:

```
FOLDERS declare TOPOLOGY
  topology contains ENTITIES (entity.tsp)
  topology contains ROUTES   (routes.tsp, query/, mut/)
  topology contains RELATIONS (@belongsTo, @hasMany, @manyToMany)

EXTRACTORS read topology, produce FACTS
  flattenRoutes  → route facts  (method, path, params)         [check phase, extern fn]
  $onValidate    → relation facts (from, to, kind, via)        [post-check, $onValidate]
  sprefa         → code facts (what exists in .rs, .ts, .sql)  [external, comment-driven]
  introspection  → db facts (tables, columns, FKs, indexes)    [external, pg_catalog etc]

RULES consume facts, answer QUESTIONS
  "what REST routes exist?"           → route table
  "what GraphQL schema?"              → schema.graphql
  "what DB migrations needed?"        → diff(db facts, entity facts)
  "what types does layer X need?"     → visibility rules → minimum set
  "what's out of sync?"               → diff(any two fact sets)

EMITTERS take answers, write CODE
  into autozone blocks (generated, re-run safe)
  around manual blocks (hand-authored, preserved)
  per target language (Rust, TS, SQL, GraphQL SDL)
```

What was built this session: FOLDERS layer (convention) + first two EXTRACTORS (flattenRoutes, $onValidate relation graph). RULES and EMITTERS rows are next.

Vocabulary mapping (how the same idea appeared throughout the conversation):
- "collapse layers into least output types" = one model declaration, N projections, each projection takes only its slice
- "dip in and out of autozone" = folder tree is hand-authored, projections are generated, boundary is per-file/per-block/nestable
- "sprefa collecting facts from comments" = folder tree is one fact source, code in other languages is also a fact source, both feed the same reasoning layer
- "why not GraphQL" = don't want ONE projection target, want the thing that projects to ALL targets
- "Prolog for reconciliation" = projections can disagree (DB has column TSP doesn't model), something finds those gaps
- "Mercury compiles types to C" = declaration IS compiler input, targets ARE compiler output, rules ARE the compiler

The reason it felt combinatorially explosive: RULES × EMITTERS is combinatorial, but facts are uniform (key-value tuples), rules are composable (add a rule, don't rewrite an emitter), emitters are independent (adding GraphQL doesn't change REST emitter). The architecture constrains the explosion.

GraphQL ↔ REST 1:1 mapping confirmed: namespace tree emits both. 1:M → GQL field resolver, M:M → GQL field + junction mutations, M:1 → GQL field on child type. Freeform muts → named GQL mutations. GraphQL is a projection target, not a replacement for the declaration layer.

Mercury insight: type system description as facts, per-target rules as emitters. The strongest-target-expressible intermediate needs sum types + parametric polymorphism + row polymorphism minimum.

The entity-relation graph extracted here IS the fact set that Prolog would consume. Each edge is a Prolog fact: `relation(user, org, belongs_to, org).`
