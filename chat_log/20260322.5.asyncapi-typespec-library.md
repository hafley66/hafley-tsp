# Session: asyncapi-typespec-library

## Goal
Build a TypeSpec library that encodes AsyncAPI 3.x's object model as TypeSpec decorators, enabling both AsyncAPI YAML spec generation and Rust handler codegen from the same TypeSpec source.

## Current State
Task 1 complete: @hafley/typespec-asyncapi package created with .tsp decorator declarations and JS implementations. Committed as 62ba5d2. Tasks 2-4 remain.

The library defines decorators for: @server, @channel, @send/@receive, @reply, @correlationId, @payload, @messageHeader, @contentType, @amqpBinding, @amqpOperationBinding. All follow @typespec/http's pattern (extern dec in .tsp, stateMap in JS, accessor functions for emitters).

## Problem/Context
The existing transport binding system (HTTP + WS) had no concept of channels, direction, reply patterns, or protocol bindings. AsyncAPI already solved the abstraction across 15+ protocols. Rather than reinventing, we encode AsyncAPI's object model into TypeSpec as the authoring surface, then emit in two directions: AsyncAPI YAML (spec) and Rust handlers (implementation).

## Solution/Approach

### Architecture
```
TypeSpec + @typespec/http    --> OpenAPI spec (exists) + Rust HTTP handlers (exists)
TypeSpec + @hafley/asyncapi  --> AsyncAPI 3.x YAML (new) + Rust broker handlers (new)
```

### Key design decisions (locked)
1. Route/channel unification: @route and @channel use the same {param} syntax. Emitter translates delimiters per transport (slashes for HTTP, spaces for CLI, dots for AMQP/Kafka).
2. Process-space decoupling as complexity axis: CLI (process-local, simplest) < HTTP (transaction, two processes) < AMQP (decoupled, N processes + external broker storage).
3. Stream<T> works at every level: CLI = stdin/stdout, HTTP = SSE/chunked, WS = frames, AMQP = consumer loop. Stream shape (unary/server/client/bidi) inferred from signature.
4. Every stream has start and stop. A transaction is a stream of length 1 in each direction.
5. HTTP operations use existing @typespec/http decorators, NOT our new decorators. Our decorators only appear for broker/async protocols.
6. AMQP is the right complexity target for the handler-code emitter. It exercises all core primitives without bleeding into infrastructure provisioning (which is Terraform territory).
7. Bindings at 4 levels (server/channel/operation/message) matching AsyncAPI's model. HTTP collapses channel into server (no-op). Brokers need all levels.

### Three-level constructor model (universal)
1. Server (connection/transport) -- bind port, amqp connect, etc.
2. Channel (infrastructure setup) -- HTTP: no-op; AMQP: queue_declare/exchange_declare
3. Operation (message handling) -- HTTP: .route(); AMQP: basic_consume + dispatch

### AsyncAPI gap analysis done
Surveyed all 15 AsyncAPI binding specs (AMQP, Kafka, MQTT, NATS, SQS, SNS, Solace, Google Pub/Sub, HTTP, WS, etc.). Features beyond AMQP (Kafka message keys, SQS DLQ chains, Solace multi-destination fan-out) are all protocol-specific binding config, not core primitives.

## Key Insights

### AsyncAPI structure
AsyncAPI separates WHAT EXISTS (servers, channels, messages) from WHAT HAPPENS (operations) from HOW per-protocol (bindings as overlays). Channels are the pipe definition (address + message types + infra config). Operations are what an app does with a channel (send/receive + message subset + reply pattern).

### Why AMQP is complex
AMQP decomposes a message flow into independently configurable pieces that HTTP welds together. Exchange (routing point) + Queue (delivery point) + Binding (routing rules) + Consumer (processing) are all separate. HTTP collapses all four into Router::new().route("/path", handler).

### Protocol binding survey findings
- AMQP: channel bindings = queue/exchange declare; operation bindings = ack, delivery mode, priority, cc/bcc
- Kafka adds: typed message key (partitioning), consumer groups, schema registry (server-level)
- MQTT adds: QoS spectrum (0/1/2), last will and testament
- SQS adds: DLQ chains, FIFO queues, IAM policies (infrastructure-as-code territory)
- Solace adds: multi-destination fan-out with per-destination topic subscriptions

### TypeSpec ecosystem status
- No official @typespec/asyncapi exists. Issue #2463 open since Oct 2025, in backlog.
- @typespec/events (event unions), @typespec/streams (Stream<T>), @typespec/sse exist as building blocks
- One community alpha (LarsArtmann/typespec-asyncapi, 12 stars, early)
- Strong enterprise demand (SwissPost, Sportradar, others)

## Open Questions
- Should fire-and-forget be a stream shape or void-return unary?
- How to express "this transport doesn't support this stream shape" (null cell vs compile error)?
- Per-message bindings (MQTT QoS, Kafka partition key): separate decorator namespace per protocol, or generic @messageBinding?
- Generated-defs type safety: should we run tspd to generate decorator type interfaces from .tsp?
