# Session: emit-helper-target-lang

## Goal
Build a shared emitter helper package (@hafley/emit-helper) that extracts common subproblems across TypeSpec emitters into a pluggable TargetLang interface, so writing a new emit target is just implementing ~10 methods.

## Current State
- Package built and tested: `packages/emit-helper/` with 11 passing tests
- Three TargetLang implementations: plain Rust strings, JSON Schema objects, Alloy JSX (with refkeys)
- Also fixed TypeSpec parse errors in asyncapi models and got tsp-dot graph tool working end-to-end
- Nothing staged/committed yet -- user was asked what to include/exclude before commit

## Problem/Context
Two existing emitters (Rust via Alloy, React via Alloy) had overlapping subproblems: scalar mapping, container wrapping (optional/array/map), name policy, reference handling, declaration rendering. No shared abstraction existed. User wanted to identify common emitter subproblems and build a reusable interface.

## Solution/Approach
`TargetLang<TType, TDecl>` interface generic over both type representation and declaration output:
- TType: string (plain Rust), JsonSchemaType (JSON Schema), RustType with Children (Alloy)
- TDecl: string/RustDecl (plain), JsonSchemaDecl (schema), AlloyRustDecl with JSX+refkey (Alloy)
- Walker `emitAll(types, target)` handles recursion, optional wrapping, field mapping
- Consumer places output into auto zones -- helper stays zone-agnostic

Also fixed three TypeSpec gotchas (backpropped to skills):
1. `is` reserved keyword needs backtick escaping
2. Inline anonymous models not valid TypeSpec
3. Compiler parse errors cascade silently, must check program.diagnostics

## Key Insights
- TargetLang<TType, TDecl> generic over both dimensions lets plain strings, JSON objects, and Alloy JSX all use the same walker
- Alloy integration works via buildRegistry() for refkey pre-allocation + createAlloyRustTarget(registry)
- The helper stays zone-agnostic -- consumers place output into AutoZone/ManualZone
- Neutral TypeDef types (promoted from rust emitter) are the bridge between TypeSpec compiler and any target
- AsyncAPI bindings (AMQP exchange config, partition counts) are runtime deployment config, not type structure -- user grasps this distinction and wants clean separation

## Open Questions
- Should packages/rust reuse @hafley/emit-helper types or keep its own copy?
- Does the enum member naming need a separate hook vs reusing typeName?
- How to handle decorator-driven emit decisions (e.g. @channel → AsyncAPI channel object)? Current TargetLang only handles type structure, not decorator state.
